## V8 现场结果与 V9 巡检总线节奏

V8 的手动点动连续完成了多组 UP/LEFT 动作，没有出现 `TIMEOUT`。同一次现场测试
中，四点巡检两次都在 `LT-IN1 step=1/28 seg=3/3` 的缓冲写入阶段中止：

- 第一次 M4：`rx_len=0/expect=8`、`elapsed=251 ms`，无 `uart_error`。
- PA0 自动回中心重试后，第二次 M2：`rx_len=0/expect=8`、
  `elapsed=251 ms`，无 `uart_error`。

两次都是完整的 DMA 接收窗口内完全没有应答，不再是 V7 的 ORE/半帧问题。
失败地址从 M4 变成 M2，也不能归因为某个固定电机或 `(-4.00,4.00) cm` 路径
边界。巡检与手动的关键差异是：巡检每个 segment 自动连续执行四台缓冲写入、
同步触发，并在运动完成后读取四台编码器；手动由操作者分组触发且没有每段四台
编码器轮询，因此总线事务密度较低。

V9 保留每个 segment 的编码器采集，不牺牲拟合数据，同时只放宽巡检节奏：

- 手动点动四台写入间隔仍为 `60 ms`。
- 巡检四台缓冲写入间隔由 `60 ms` 改为 `100 ms`。
- 巡检逐台编码器读取间隔由 `15 ms` 改为 `80 ms`。
- 四台编码器读完后增加 `120 ms` 总线静默，再开始下一段。

相对缓冲命令一旦无应答仍不盲目重发、不执行同步触发。上述改动用于验证
“巡检事务密度”因素，不代表已经排除 RS485 自动方向、接线、终端、共地、
驱动固件和供电问题；这些现场根因仍为“待确认”。V8 证据保存在
`data/manual_jog_evidence_2026-07-24-v8.csv` 和
`data/patrol_evidence_2026-07-24-v8-run4.csv`。

## V10 USART3 预开 DMA 接收

V9 降低了巡检事务密度，但通信层仍存在一个软件窗口：对普通 `0x10` 缓冲写，
旧流程是 `TX complete` 后再打开 DMA 接收。如果某个驱动在自动方向 RS485
转换器切回接收前后很快回应，MCU 可能在完整 `MB_RX_TIMEOUT` 窗口内看到
`rx_len=0`。V10 对读命令和 `0x10` 多寄存器写改为发送前预开 USART3_RX DMA，
再从 DMA 字节流中按地址、功能码和 CRC 查找真正应答。

安全边界不变：

- `0x06` 单寄存器写仍保持发完后再接收，避免把本机回显误判为驱动确认。
- `TIMEOUT/CRC_BAD/REJECTED/FRAME_BAD/TX_FAIL` 后仍不重复相对缓冲命令。
- 缓冲失败后仍不执行同步触发。
- `MB_RX_TIMEOUT` 从 `250 ms` 放宽到 `400 ms`，用于容纳驱动偶发慢应答；这不代表
  现场 RS485/供电根因已经确认。

## 2026-07-26 接收实现 A/B 结论

`Q2-CAL-JOG-v12-Q3-RXSW1` 使用 `BLOCKING_BYTE` 跑相同 LT 路径时得到两类故障：

- M2 编码器 `0x03`：`rx_len=0/expect=11`、`elapsed=403 ms`。
- M2 缓冲写 `0x10`：`rx_len=0/expect=8`、`elapsed=403 ms`，同步触发未执行。
- 重回中心再跑后，M1 编码器 `0x03` 收到
  `01 03 06 00 00 08 5C 00 00`，即 `9/11` 字节，同时
  `uart_error=0x00000008`。

最后一条明确证明阻塞逐字节接收会发生 USART3 ORE，丢失电机已经发出的回复；
因此默认已恢复 `DMA_SCAN`。`rx_len=0` 没有被这条证据解释，仍可能来自驱动未发、
